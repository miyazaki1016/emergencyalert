# 接近予測エピソードと重複送信の修正

## 所在・今回の境界
- ブランチ：`fix/forecast-notification-episodes-20261029`。作業前main `37294ed7b9961501c4b07e2388af7a2a5a89f20e`、本番watch-rain v32を照合。
- [PR #103監査](BIFUKA_NOTIFICATION_AUDIT_20261029.md)、[PR #93研究](https://github.com/miyazaki1016/emergencyalert/pull/93)、PR #63のdeliveryAttemptSafetyを確認。既存ラボ・画像回収・点面シャドー処理は再実装しない。
- ユーザーの実機確認：539の理由、雨量区分、250/500/1000m占有率の表示成功。本資料は新たな通知修正と除外理由表示の追加を扱う。

## 根本原因
対象の実通知は美深町538/539、羽田540/541/542、自宅543/546/547/548。各不変snapshotで直前last_notified_atがあり、clear_streak=2→3または3で飽和。現況 `episodeClosed=clear_streak>=3` が送信判定のlastNotifiedAtをnull扱いし、継続中の未来ACTIONABLE予測を再通知させた。羽田の途中のINFOも、将来の雨が解消したことを意味しない。

指定9件は異なる巡回の通知であり、並行cronの競合と同一原因ではない。旧workerには独立に read→Push→履歴→状態 の競合・クラッシュ再送リスクもある。

## 予測エピソード
- `rain_watch_runtime` に現況とは独立した予測エピソードID、接近通知済み、強雨通知済み最高段階、予測解消の確認回数、最後の発表時刻を保持。
- 将来に雨色がある間は同じ予測エピソード。現況が透明3回以上、ACTIONABLE→INFO、予測開始時刻の更新、弱雨への変化だけでは解除しない。
- 既存解釈エンジンが完全な予測フレームからDRYとした状態を、異なる新しい発表時刻で3回確認したときに予測エピソードを終了。UNKNOWN・不完全・時刻不明は解消の証拠にせず、解消確認の連続回数を0に戻す。同一・古い発表は回数を増やさない。
- その後に新しい雨予測が現れたら新IDを発行し、最初のACTIONABLEは再通知可能。新規エピソードの最初の通知を3回雨観測まで待たせる仕様ではない。
- 既存状態の初回移行は、通知後の直前の発表履歴（最大20行）に、異なる発表で3回連続RAIN_CLEARが確認できれば解除済み扱い。直後に弱雨の接近予測が入っていても、その解消を引き継ぐ。それ以外は既存last_notified_atを保守的に引き継ぐ。過去の配信記録がない地点は未通知。移行時に既存通知を一斉再送しない。
- 強雨は別キーで、通知済み最高段階より上への30→50→80mm/h悪化を許可。現況雨なし3回で最高段階をリセットしない。従来のJMA14桁をnew Dateへ渡す問題も専用timestampで修正。通知OFFは全種類で尊重。

## 並行実行・DB障害を分けて対策
- targetごとに原子的claimで2分のleaseを取得。別workerはBUSYとしてスキップ。状態保存と購読別claimはlease ID・有効期限でfenceし、古いworkerの状態上書きを拒否。
- `rain_push_attempts` は既存の配信履歴と分離し、Push前に `UNIQUE(target,event_key,subscription)` で送信権を永続化。event_keyはエピソードID＋APPROACH／ENDING／SEVERE段階。発表時刻や予測開始時刻ごとに新キーを作らない。
- claimが得られた購読にだけ送信。ACCEPTED／FAILED_TERMINAL／UNCERTAINを記録。送信中のtimeout・5xx・408/429は不明扱い。期限切れ・クラッシュ・結果保存失敗のCLAIMEDも自動再送しない。
- 全購読処理後にエピソードの通知済みを保存。途中クラッシュ時は未処理購読へ進めるが、既にintentを持つ購読は再送しない。履歴やwatch_statesの保存失敗で送信済みを忘れても、永続intentが抑止する。
- 端末への厳密なexactly-once到達は保証しない。不明送信の無条件再試行をしないため、届かなかった可能性は残る。CLAIMED/UNCERTAINを監査対象にし、手動で無条件解除しない。
- 両テーブルはRLS有効・service_roleのみ。新関数はSECURITY INVOKERでPUBLIC/anon/authenticatedのEXECUTEを剥奪。端末鍵・endpointは新テーブルへ保存しない。既存データを削除しない。attemptの自動削除は今回実装せず、将来は現役episodeの一意性を壊さない保持設計が必要。
