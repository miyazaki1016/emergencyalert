# National rain queue lease-fencing contract proposal

Status: **implemented on the PR #59 proof branch; isolated PostgreSQL CI verification pending; not Production-ready**.
Related blocker: `docs/NATIONAL_RAIN_READINESS_PROOF.md`, section “2026-10-10 Queue lease fencing audit”.
PR #59 remains an experiment. This document does not authorize a canonical schema change, migration application, Storage writes, deployment, or merge.

## 1. Failure to prevent

A claim's five-minute expiry allows worker B to reclaim a job still executing in worker A. If A later writes a result or calls finish/defer using only the job ID, it can mutate B's current attempt. A client timeout or abort is advisory; only the database can atomically reject stale ownership.

## 2. Required ownership invariant

Every successful claim creates a **new, unrepeatable claim identity**. The identity is scoped to one job attempt and is replaced on every successful reclaim. All state-changing operations must prove that their identity is still current inside the same database transaction that performs the write.

Suggested representation (choose one during review):
- random `lease_token UUID` generated by the database on each claim; or
- monotonic per-job `claim_generation BIGINT` incremented atomically on each claim.

A random token is simpler to compare; a monotonic generation is easier to audit. Either is acceptable only if it is generated/changed atomically by the claim RPC, returned to the worker, never accepted from an untrusted caller as the source of truth, and checked by every mutating RPC. Do not rely on `attempts` as a fence unless its increment, returned value and every conditional write are proven atomic and non-reusable.

## 3. Proposed RPC contract (signatures are illustrative)

- `claim_national_rain_refinement_jobs(p_limit)` returns each claimed row with `id`, job payload, `lease_token` (or `claim_generation`), and `lease_expires_at`. The RPC locks eligible rows with `FOR UPDATE SKIP LOCKED`, then atomically marks each PROCESSING, sets its new identity and claim/expiry timestamps, and returns that exact identity. A reclaim must always rotate the identity.
- `save_national_rain_refinement_result(p_id, p_lease_token, p_result...)` validates that the row is still PROCESSING and the supplied identity equals the row's current identity, then writes the result in the **same transaction**. A stale owner must not be able to overwrite an existing/newer result. Prefer one RPC that performs ownership validation and result persistence together; a separate “check ownership” followed by an independent upsert is racy.
- `finish_national_rain_refinement_job(p_id, p_lease_token, p_success, p_error)` changes state only when id, PROCESSING status and current identity all match.
- `defer_national_rain_refinement_job(p_id, p_lease_token)` likewise changes availability/state only when id, PROCESSING status and current identity all match.

The proof-branch implementation uses a UUID lease token and changed RPC signatures. The migration remains proof-only and must not be applied to Production; any canonical migration requires separate review and authorization.

## 4. Stale-lease semantics

For a well-formed request whose token no longer owns the job, return an explicit outcome such as `STALE_LEASE` (preferred for observability) or a documented zero-row result. Do not treat stale ownership as a transient success, retry the mutation with a newly fetched token, or silently overwrite the newer attempt. The worker should discard its result, record a bounded diagnostic, and stop mutating that job.

For a current token, normal success/failure/defer semantics apply. Repeated calls with the same current token should have documented idempotency behavior. After terminal completion, that token must not reopen or alter the job.

## 5. Atomicity and result consistency requirements

1. Claim eligibility, row lock, identity rotation, PROCESSING transition and returned identity are one transaction.
2. Result ownership validation and result write are one transaction; there must be no check-then-upsert gap.
3. Finish/defer ownership predicate and status transition are one atomic conditional mutation.
4. A stale worker cannot modify either queue state **or** the result row after a reclaim.
5. Result rows should retain enough provenance to audit the producing claim (at least job id and claim generation/token fingerprint if approved), without logging a secret lease token.
6. If result save and finish are separate RPCs, expiry/reclaim between them must make finish return stale and must not allow a later stale save. The design must explicitly decide how a valid saved result is reconciled if the finish call fails. A single transaction/RPC that validates ownership, stores the result and marks completion is safer where workflow semantics permit it.
7. Lease renewal, if later added, must also require the current identity and cannot resurrect an expired/reclaimed identity.

## 6. Required concurrency proof before rollout

Use an isolated disposable database/schema with the proposed migration applied there—not Production—and a deterministic clock/lease seam where practical.

- **A → expiry → B:** A claims generation/token A; its lease expires; B reclaims and receives a distinct B identity.
- **Stale result:** A's result write is rejected and the stored result remains unchanged; B's result write succeeds.
- **Stale finish/defer:** A's finish and defer are rejected; B can finish successfully.
- **Concurrent reclaim:** two claimers race for one eligible job; only one owns the resulting current identity and the other cannot act as that owner.
- **Boundary:** test just before expiry, at/after expiry, and reclaim concurrent with A's write. The database transaction ordering must produce one valid winner, never a stale mutation.
- **Retry/idempotency:** duplicate current-token requests, database/network timeout after commit, terminal rows, and failed result writes have explicit expected outcomes.
- **Regression:** existing queue lifecycle, retry, unique-job and result-shape tests remain green.

The proof must inspect persisted state and results after each race, not just assert TypeScript calls or mocked RPC arguments. Save reproducible test output and the exact migration/commit SHA.

Existing id-only callers must not retain a mutation path that bypasses fencing.

After approval, implement on a feature branch and run unit tests plus the isolated DB concurrency proof. Keep rollout disabled until those pass. ## 8. Exact current call-site audit

Source review at PR head `9c712b3378b9ccfbcb859fc2799f2472d0e6d1a1` confirms the issue is not limited to the RPC signatures:

- `lib/weather/rain/nationalRainQueue.ts::claimNationalRainJobs` returns rows without a lease identity because the claim RPC currently returns the queue table row as-is.
- `saveNationalRainRefinementResult` performs a direct table upsert keyed only by `job_id`; this bypasses any future fencing unless replaced by the ownership-checking RPC.
- `finishNationalRainJob` and `deferNationalRainJob` pass only `p_id` to their RPCs.
- `lib/weather/rain/nationalRainWorker.ts::processNationalRainRefinementJobs` saves a z10 result **before** it calls finish. If the finish later discovers that the lease is stale, the already-written result may have overwritten the newer attempt's data. Fencing finish alone therefore does not solve the race.
- The deadline path calls defer by ID only, including for jobs claimed but not started.
- The CI step “Prove national rain queue lifecycle” applies the proof migration in a disposable Postgres service and exercises claim/finish/defer, but currently does not simulate lease expiry/reclaim or stale result writes.

### Required call-site changes after contract approval

1. Extend `ClaimedNationalRainJob` with the returned lease identity and carry it unchanged for the entire invocation.
2. Replace direct result-table upsert with the atomic fenced result RPC (or a single fenced complete-with-result RPC). Do not leave a service-role direct-table write path that bypasses the ownership predicate.
3. Pass the same identity to finish and defer. Treat `STALE_LEASE` as a stale result to discard, not as a generic success/failure to retry with the current token.
4. Ensure a job claimed but not started is deferred with that exact identity; if a concurrent reclaim has already rotated it, the defer must be rejected safely.
5. Add a disposable-Postgres integration proof to CI that forces A's lease expired, claims it as B, then verifies A's result/finish/defer are rejected and B's result/finish succeed. Assert the persisted result is still B's, not merely that a function returned without error.
6. Review enqueue behavior separately: enqueuing child jobs is idempotent under the unique key and does not complete the parent. A stale parent must not mark itself done; whether child enqueue itself must be ownership-conditional should be decided explicitly to avoid stale attempts expanding the queue after reclaim.

This was the pre-implementation source audit. The follow-up now implements the proposed fencing contract on the proof branch; its isolated PostgreSQL CI test is the required race reproduction. No Production database or Storage state was modified.


## 9. Proof-branch implementation (2026-10-10)

- The claim RPC now rotates and returns a database-generated lease_token for every claim/reclaim.
- The completion RPC checks id + PROCESSING + lease_token and atomically completes the parent, persists an optional z10 result, and/or enqueues bounded child jobs. A stale owner cannot persist results or expand the queue.
- Finish and defer require the same lease token and return STALE_LEASE when it no longer owns the row. Legacy ID-only overloads are dropped in the proof migration.
- The worker carries the returned token through every mutation and no longer writes the result table directly. Ambiguous completion responses are not converted into a second mutation using a different identity.
- The disposable-Postgres CI proof covers A claim → expiry → B reclaim, token rotation, rejection of A's result/finish/defer, persistence of B's result, rejection of stale child enqueue, and atomic child enqueue for a current owner.

- The migration and runtime changes are isolated to the unmerged PR proof branch. Production remains untouched and rollout remains blocked.
