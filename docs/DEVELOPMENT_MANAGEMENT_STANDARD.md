# 共通開発台帳・自動棚卸し運用規約（アメふる／美咲）

更新: 2026-10-31。これは管理方法の統一案であり、既存の棚卸し結果や実装記録を置き換えない。

## 正本と入口
- **main の総覧は入口・索引**。開発の詳細証拠は専用ブランチの資料を正本として残す。
- **main の開発台帳は作業単位の進捗一覧**。既存の詳細資料を複製せず、リンク・検証状態・次の一手を示す。
- アメふる: `docs/PROJECT_OVERVIEW.md` → `docs/DEVELOPMENT_LEDGER.md` → 作業別資料。
- 美咲: `docs/IMPLEMENTATION_OVERVIEW.md` → 新しい `docs/DEVELOPMENT_LEDGER.md`（索引）→ 既存の `docs/DEVELOPMENT_REGISTRY.md`（`docs/development-registry-audit-20261020` ブランチにある詳細な棚卸し）と各作業資料。
- **美咲の116KB超の既存台帳や監査JSONを消去・短縮しない**。新しい索引は詳細への入口であり、過去の結論を勝手に更新しない。

## 各作業の必須記録
| フィールド | 意味 |
| --- | --- |
| ID / 件名 | 作業を一意に追える名前 |
| 状態 | A main実装確認 / B ブランチ実装・main未確認 / C 実験・検証不足 / D 設計・監査のみ / U 未判定 |
| 所在 | ブランチ・PR・Issue・詳細資料のパス |
| 証拠 | 確認したcommit・テスト・実機・本番記録（確認日を付ける） |
| 未確認 | main・本番・品質について証明できないこと |
| 次の一手 | 具体的な作業、実施前の承認要否 |
| 更新日 | 最後に証拠を確認した日 |

状態Aは「本番稼働」を意味しない。本番反映・実機確認は別フィールドで記録する。PRのCI成功やahead差分だけで完成と判定しない。

## 自動化の位置づけ
- `.github/workflows/development-inventory.yml` が毎週月曜 10:17 JST にGitHubのブランチ、open PR、open Issueを**読み取り専用**で収集する。
- `scripts/development_inventory.py` は「open PRがないブランチ」「14日以上更新がないPR/Issue」を**調査候補**として出す。
- 結果はActionsの実行概要と30日保存のJSON/Markdown artifactで確認する。**台帳の自動書換え、Issue作成、ブランチ削除、マージ、デプロイはしない**。
- open PRがないブランチは完了済み・閉鎖済みPR・研究保存ブランチの場合もある。候補を「忘れ物」と断定する前に、mainの実装、merged/closed PR、既存台帳の証拠と突き合わせる。
- GitHub Actionsのscheduleは**mainへマージ後に初めて有効**。本PRがDraftの間は実行開始していない。

## 引き継ぎ時の順番
1. main総覧とmain開発台帳を読む。
2. 該当作業の専用ブランチの詳細資料とPRを取得する。
3. mainのコード・コミット・本番状態を**別々に**照合する。
4. 自動棚卸しの候補をレビューし、既存台帳との一致・未登録・要再確認を分類する。
5. 事実と未確認事項、次の一手を更新する。自動化が示す候補を根拠なしに「未完了」と書かない。

## 安全境界
この管理作業はアプリの仕様、DB、Push、実運用を変更しない。PRの統合、ブランチ削除、本番変更には個別の承認を要する。

## 台帳統一の移行ルール（2026-11-01）

- **再監査は差分優先**：既存の確認済み証拠を維持し、最新main・ブランチhead・PR/Issueと矛盾する箇所、未登録の作業、根拠が欠けた項目だけ再確認する。古い証拠は確認日を明示し、現在の状態へ自動昇格しない。
- **統一台帳の1行＝1作業**：ID・件名・状態A/B/C/D/U・ブランチ/PR/Issue/詳細資料・証拠（日時/commit）・main統合・本番反映・DB適用・実機確認・未確認・次の一手・更新日を保持。判定できない項目は「未確認」と書き、空欄を「未実施」とみなさない。
- **証拠の保存先**：台帳は短い索引。アメふるの既存台帳・総覧・個別資料、美咲の詳細台帳（専用ブランチ）・監査資料を削除、短縮、無断移動しない。既存履歴と索引のリンクを保つ。
- **棚卸しの突合順**：①既存台帳の作業IDを保持、②全ブランチ・open/closed/merged PR・open Issueを取得、③既存記録との対応表を作成、④新規・状態不一致・要証拠を抽出、⑤対象のみ再調査。open PRなし／長期更新なしを未完了と断定しない。
- **安全ゲート**：管理ブランチとDraft PRで差分を検証。mainマージ・週次schedule有効化・アプリ本体/DB/Push/本番変更は別途承認を要する。
