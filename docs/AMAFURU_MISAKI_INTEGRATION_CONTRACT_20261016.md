# アメふる（EmergencyAlert / サキクル）× 美咲 気象・防災連携 — 共同設計契約案
最終更新: 2026-10-16 / 状態: **構想・設計合意（Draft）**。API実装済み・本番連携済みではない。

> **未来のアメふるのソラ、美咲のソラへ:** これは双方のユーザーが明示した横断設計方針。別々に同じ公式気象情報を取得・解析する仕組みを作り込まない。まずこの仕様を読んで最新main・作業PR・総覧と照合し、実装済み／未実装を分けて進める。最終的なAPI仕様は双方のレビュー後に固定する。

## 1. 不変の責務分担

- **アメふる（提供側）:** 気象庁等の正式な公式情報の取得、地域・対象地点判定、雨・強雨・警報・災害の事実・予報区分の判定、データ欠損／鮮度／確度、エピソード／重複可能性の識別。公式データにない予測・補間・安全断定をしない。単独サービスとして成立させる。
- **美咲（利用側）:** ユーザーが許可した対象地点・キャラクターの設定地域を選ぶ。アメふるの機械可読な判定を根拠に、会話への関連性・通常通知の要否・相手との関係性に応じた言葉を決める。人格・記憶・恋人段階をアメふるへ渡さない。
- **安全境界:** 災害の深刻度、公式警報・避難指示、発表対象地域、重要通知の安全基準は決定的ロジックで扱い、Geminiが捏造・格下げ・抑止できないようにする。実際の緊急通知経路は個別の安全設計とレビューが必要。
- **共通化の範囲:** データの正本化・解釈をアメふるへ集約。美咲の人格／関係性の会話化とユーザーごとの通知頻度は美咲固有。アメふる自身の生活通知アルゴリズムを美咲へ無条件に適用しない。

## 2. 連携順序

1. **Phase A（最初）:** 美咲のサーバーから認証付きでアメふるの読み取り専用APIへ問い合わせる Pull方式。まず降雨の現在観測・短時間予測・UNKNOWN・有効期限だけを対象にする。認証・キャッシュ・レート制限・遅延／障害時フォールバックを準備する。
2. **Phase B:** 地域イベントの種類を拡張（強雨、猛暑／WBGT、公式気象警報、地震、台風、避難情報）。**アメふる側の公式情報処理と実装済み判定が確認できる項目だけ**公開する。種類の列挙は実装宣言ではない。
3. **Phase C:** 通知用イベント配信（Webhook/QueueなどのPush型）を別契約で検討。署名・リプレイ防止・順序の逆転・重複配送・再試行・受信確認・購読地点・通知抑制・安全例外を先に設計。今すぐ実装しない。

## 3. データ契約の候補（例示・確定スキーマではない）

```json
{
  "schemaVersion": "weather-context.v0-proposal",
  "eventId": "example-rain-001",
  "kind": "RAIN_START_EXPECTED",
  "status": "forecast",
  "location": { "areaCode": "EXAMPLE", "label": "東京都江東区", "spatialResolution": "point-or-area" },
  "issuedAt": "2026-10-16T08:40:00+09:00",
  "observedAt": null,
  "validFrom": "2026-10-16T09:00:00+09:00",
  "validUntil": "2026-10-16T09:30:00+09:00",
  "receivedAt": "2026-10-16T08:45:00+09:00",
  "source": { "provider": "JMA", "product": "official-forecast", "reference": null },
  "quality": { "state": "VALID", "reason": null },
  "payload": { "intensityMmH": 8, "rainStartMinutes": 20 }
}
```

**すべて架空例。実際のJMA値・現在の天気・実装されたAPIレスポンスではない。**

最低条件:
- `schemaVersion`: 後方互換・非互換変更を検知。未知バージョンはfail-closed。
- `eventId`: 同一事象の重複抑制に使う。ただし訂正・予報更新と同一イベントを混同せず、必要ならrevision/episode IDを別定義。
- `kind`: 事象型を表す。例 `RAIN_START_EXPECTED`, `RAIN_CONFIRMED`, `RAIN_ENDING_EXPECTED`, `HEAVY_RAIN_FORECAST`, `OFFICIAL_WARNING`, `EARTHQUAKE_OBSERVED`。正式列挙は別途承認。
- `status`: `forecast` / `observation` / `official_announcement` を明確に分ける。予報値を観測事実として語らない。
- `location`: 緯度経度・都道府県名だけでなく判定解像度／対象区域／地域コード、必要に応じて空間的な曖昧さを表す。対象地点の雨と自治体全域の警報は意味が違う。
- `issuedAt` / `observedAt` / `validFrom` / `validUntil` / `receivedAt`: 発表、観測、有効期間、取り込みの時刻は混同しない。タイムゾーン明示。
- `source`: 公式プロダクト・出典を追跡可能にする。URLなどは確定したものだけ。
- `quality`: `VALID` / `UNKNOWN` / `STALE` / `FETCH_ERROR` などを明示。UNKNOWNをNO_RAINに変換しない。欠損は安全の証拠にならない。
- `payload`: イベント種別別の型定義を別に設ける。降雨強度と警報区分を混同しない。30/50/80mm/hの強度は警報発令とは別。
- 個人識別子、恋人関係・会話内容・長期記憶・API秘密鍵をレスポンスに含めない。

## 4. 地点とプライバシー

美咲側は **(A) ユーザー登録地点、(B) 許可された現在地、(C) キャラクター設定上の生活地域** を分けて保持・選択する。必要な地点の問い合わせだけ行う。現在地の取得許可・精度・取得時刻を明示し、古い位置を現在地と断定しない。

アメふるへは提供に必要な位置・地域情報だけを渡す。ユーザーIDやキャラクターIDを渡さずに処理できる契約を優先。地点のキャッシュ、アクセスログ、保持期間と再識別リスクをレビューする。警報は地点一致だけで機械的に除外しない。

## 5. 美咲側の統合ゲート

- 美咲 `app/api/chat/route.ts` 等に既存の天気・東京生活イベント取得処理がある。**即削除禁止**。現行の会話品質・天気事実・欠損時の動作を回帰試験で比較してから段階移行。
- 応答不可・情報鮮度切れの場合、美咲の会話全体を落とさず「確認できない」と扱う。古い情報を新しい情報として使わない。
- 関係性に応じて文体は変えてよいが、観測値・発表対象区域・予報/観測区分・緊急度を変えない。
- プロアクティブ通知は、通常の気遣い頻度・quiet hours・同意・重複防止を設計。**緊急防災通知の例外は別設計**。
- 複数キャラクターで気象データキャッシュは共有できるが、人格・関係・個別記憶・通知嗜好／履歴はユーザー×キャラクターごとに独立させる。ユーザーが同意した共通地点のみ共有。
