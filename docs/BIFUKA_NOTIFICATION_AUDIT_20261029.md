| worker | 定時・通常の終了条件 | 終了後 |
|---|---|---|
| evaluate-rain | 5分、全必要実況回収／対象無効／target+50分／24claim | COMPLETEまたはINDETERMINATE。足りない時刻と理由を保持 |

通常終了しても、例外ルートではevaluate/archiveのcatchが期限・最大回数によるterminal化を実行しない。画像／shadowの容量32MiB以上ではclaim自体が止まり、PENDINGが残り得る。shadowのcatchは24claimでINCOMPLETEにするが、通常ルートと異なり期限だけでは閉じない。この2件では発生していない。例外・容量時にもterminal化する専用の終了処理と、終端理由の永続化を追加する修正案を残す。故障注入・lease競合・実データを壊さない試験後に別改修とする。

計画は評価対象前後の画像13枚／ケースで、snapshot予測12コマ全部の画像保存ではない。shadowには以下の保留が残る。
- IMAGE_MISSING：評価窓の外など、画像保存計画に含まれない予測コマ。最終COMPLETEでも全コマの画像がある意味ではない。
- COARSE_SOURCE_HORIZON：538の13:15予測は12:40発表から35分先で、元データ解像度の制限により面候補から除外。
- POST_VALID_RETRIEVAL：539の12:55コマを12:56以後に回収。対象時刻後の予測画像として保留。通知判断時点より前のコマなので未来の共通採点対象にも入れない。
- 確認情報なし：現地／地点カメラの正解記録は別途必要。今回、地上観測の入力や推測はしていない。

実況答え合わせの最終値は538がexact=MISMATCH、±5=MISMATCH、±10=MATCH。539は全てMISMATCH。対象時刻の中心はいずれもRAINであり、これを「雨が全く降らない空振り」と読んではいけない。現在の評価は雨色の降り始め遷移を見ており、実況の弱雨は12:55から。一方通知の対象は生活行動向けの雨（1〜5mm/h等）の開始13:05／13:10で、評価対象の意味にも差がある。弱雨の始まりと生活行動閾値の始まりを分けた評価を追加するのが残課題。

## 4. 10分差の再通知の根拠と修正案
デプロイ済みwatch-rain v32のコードを取得し、通知判定モジュールはmainと完全一致、indexは共有ファイルimportの梱包パスと末尾改行だけの差と確認した。

| 監視時刻 | 実況有効時刻 | 中心 | 連続雨なし | 通知 |
|---|---|---|---:|---|
| 12:35 | 12:30 | 弱雨 | 0 | INFO |
| 12:40 | 12:35 | 弱雨 | 0 | INFO |
| 12:45 | 12:40 | 透明 | 1 | 538：ACTIONABLE、未通知なので送信 |
| 12:50 | 12:45 | 透明 | 2 | ACTIONABLE継続、送信済みなので抑止 |
| 12:55 | 12:50 | 透明 | 3 | 539：episodeClosedのため送信済み時刻をnull扱いして再送 |
| 13:00 | 12:55 | 弱雨 | 0 | RAINING、INFO |

539の不変snapshotは直前clear_streak=2、538のlast_notified_atあり、直前eventもACTIONABLEを保持。診断履歴の次の有効時刻12:50はNO_RAINで、advanceObservationStreakが3へ進む。別々の新しい実況時刻なので「同一時刻を何度も数えた」問題ではない。

送信判定の `lastNotifiedAt: episodeClosed ? null : previous.last_notified_at` が既存の送信済みを無効化する。保存するlast_notified_at自体をnullに消す処理ではない。さらにclear_streakは3で飽和し、episodeClosedは立ち上がりではなく値>=3の判定なので、雨なし＋ACTIONABLEが続けば次の巡回でも再通知し得る。今回の2件は5分間隔の別run・別snapshotで説明でき、並行Pushの二重送信対策とは別問題である。

修正候補（未適用）：
1. 現況の乾燥エピソードと、未来予測に対する通知済みエピソードを分離。現況雨なし3回だけで、接近中の予測通知を解除しない。
2. 予測の雨時間帯が同じ／重なる間は同一予測エピソードに紐付け、開始時刻の小さな更新で再通知しない。予測取消の継続確認や時間帯が離れた再接近でのみ新エピソード化する。
3. 再通知にはminimum gapを補助的に設ける案もあるが、強雨への悪化通知を潰さない別条件が必要。単なるクールダウンだけで根治とはしない。
4. clear_streak>=3を毎回解除する現行経路を、解除の一度だけの遷移へ改める場合も、予測接近中／弱雨の歯抜け／取消後再接近／強雨悪化／同一実況再取得の回帰試験を先に作る。

今回の追加テストは既存挙動を再現して記録するもので、再通知条件を正しいと承認するものではない。通知条件、Push送信、DB、cron、Edge Functionは変更しない。
