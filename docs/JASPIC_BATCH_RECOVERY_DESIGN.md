# JASPIC #235 / #238: 分割送信の不変条件と本番復旧ゲート

> Draft設計。実メール送信・本番DB変更・mainマージを実施しない。

## 現状の重要な危険

- 現行 `jaspic_prepare_production` は、候補の `PREPARED` 登録と**県の全スナップショット更新**を同一トランザクションで実行する。
- アプリで候補を先頭20件に切ってからこのRPCを呼ぶと、21件目以降の情報もスナップショット上は観測済みになり、次回の差分に出ない。**単純な配列分割は禁止**。
- GmailのHTTP応答が不明な `SENDING` / `UNKNOWN` は自動再送禁止。単に「前回未完了だから再送」は不可。
- #236のアプリ側 `DIFFERENCE_LIMIT` 撤去と、DB側 `>20` 制限撤去だけでは、300秒内に送信しきれる保証がない。

## 実装受入条件

1. 全候補の版・内容・宛先を固定した永続キューをDBに保持する。全スナップショットの更新は、全候補が**同一トランザクションで確実にキューへ永続化**された場合だけ許可する。既存の送信台帳・revision照合・二重実行ロックを維持。
2. 1実行の送信件数は最大20件。既存の10秒/件と60秒予備の保守的な時間判定も維持。対象外の `PREPARED` は次回の処理で安全に取得できるようにする。
3. 次回実行は既存の未送信キューを**先に**確認し、存在する場合は新規差分計算・スナップショット更新より前に処理する。キューが残っていることを「未解決異常」と混同しない一方、`SENDING` / `UNKNOWN` / `FAILED` は従来通り自動再送禁止。
4. `jaspic_claim` による原子的な取得、`jaspic_finish_production` によるGmail message ID保存、同一 `province/record_key/version` の重複禁止を維持。途中停止で `SENDING` が残れば安全停止し、手動照合まで再送しない。
5. 34件・50件・100件、途中停止、県別混在、送信済み台帳あり、Gmail結果不明、次回新規差分追加をテスト。特に **21件目以降が消失しない**ことを検証。
6. 本番の未送信分は無送信previewと配送台帳を照合し、正当な新規・更新だけを送る。CI、DB変更の検証、Vercel反映、送信結果を別々に記録する。
