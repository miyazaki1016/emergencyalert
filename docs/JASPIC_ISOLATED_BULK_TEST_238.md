## 実装上の境界

1. 既存 `public.jaspic_prepare_production` は県別20件超を拒否し、宛先を本番用に固定する。**本番関数をテスト用に緩めたり、テストで呼び出したりしない。**
2. 隔離用の専用DBプロジェクト、または本番の実データ・本番権限から切り離された独立DBを準備し、候補予約・claim・finish・snapshotをテスト専用の名前空間に閉じ込める。権限・宛先を固定し、接続先の環境識別子を検証する。
3. 34件を一括のVercel関数呼び出しにしない。PR #236 の `hasBulkSendTimeBudget` は 34×10秒＋60秒＝400秒で拒否する。**小さなチャンクの反復実行**を設計する。
4. Gmail API呼出し前に、テスト配送台帳でIDを一意に予約し、送信中を記録する。Gmail応答の `messageId` を保存して `SENT` に遷移する。応答不明・プロセス停止後の `SENDING` は `UNKNOWN` として保留し、**自動再送しない**。
5. 送信済みの同じ候補を再実行しても送信しないこと、複数のチャンクが同時に走っても二重claimできないことをSQL統合テストで検証する。
6. 送信テスト前に、34件の固定スナップショットと各候補の送信先、重複判定、個数、制限値、環境名を**無送信プレビュー**で照合する。旧データの公開日時は不明であるため「旧IDになかった」と「今回初めて公開された」は区別する。
7. 受入は34件のGmail API成功記録とmessage IDの一意性、経過時間、DB状態、エラー/不明0件を照合する。Gmail API受付は相手側の受信保証ではない。
