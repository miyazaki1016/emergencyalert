# 雨雲タイル保存容量の比較・実測手順 (2026-10-29)

## 状態
設計と容量試算のみ。**JMA実PNGのバイト数は未測定**。本番Storage/DBへの書込みなし。

## 確認済み実装
- `lib/weather/providers/jma/webMercator.ts`: zoom=10、タイル256×256画素。
- `lib/weather/providers/jma/tileUrl.ts`: `nowc/{basetime}/none/{validtime}/surf/hrpns/{z}/{x}/{y}.png`。
- `JmaPublicImageProvider.ts`: 現状は各フレームの中心1画素を取得。PNG全体の保存経路はない。
- 本番Supabase読み取り専用照会：2026-10-29時点 DB 39MB、Storage 47件 / 461,844,361 bytes（約440.4MiB）。契約プランと正確な上限はこの照会では未確認。

## 重要：半径1kmとzoom=10
- Web Mercatorの地上画素幅 ≈ 156543.0339 × cos(緯度) / 2^10 m。東京（35.6°N）では約124m/画素。
- 直径2kmは約17画素。中心の位置次第で必要タイルは1〜4枚程度（最大2×2、円の外接矩形をカバーする場合）。
- ただし**約124m画素では半径250mの比較は数画素程度**。細かな雨域形状の比較には空間解像度上の限界がある。
- 予測時点の元タイルを全て保持する方式と、必要範囲の外接矩形をロスレスPNGに切り抜く方式を比較する。切り抜き画像には元のRGBAと欠測マスク、元タイルID・画素原点を記録し、透過=雨なしと誤認しない。
- タイルPNGと、1画素を1バイトの分類値として格納する方式は**情報等価ではない**。後者はRGBAや将来の分類ルール変更に必要な情報を失う可能性がある。ロスレスRGBAなら17×17×4≈1.2KBの生画素＋マスク・メタデータ（例示、画像境界の切り方による）。

## 計測する三案
A. 取得した256×256の元PNGタイル（同じURLを重複保存せず、basetime/validtime/z/x/yで内容ハッシュを持つ）。
B. 半径1kmの外接矩形を合成して**可逆**PNGにする（取得した元画像の色・alphaを保持）。
C. 外接矩形のRGBA配列を可逆圧縮したバイナリ（gzip等）にする。**1byte降水分類への不可逆変換は別候補**。

計測項目：各方式のbytes、取得枚数、保存/復元CPU時間、RGBA完全一致、境界跨ぎ、未知色・透過、画像取得失敗、タイル重複排除率。予測時点と後続実況は別データとして集計。

## 容量の仮計算（実測値ではない）
1通知あたりの異なるフレームをF枚、フレーム当たり必要タイルT枚、元PNG平均サイズS KiBとすると、概算 = F×T×S KiB。
例：F=6, T=2, S=20KiB（**仮定**）→240KiB/通知。月100件→約23.4MiB/月、年約281MiB（メタデータ/重複排除/実況再試行を除く）。
一方、17×17の可逆RGBAの生画素は約1.2KiB/フレーム＋マスク等。**PNGサイズは実画像を取得して測るまで不明**。

## 実装前に確認すること
- JMAタイルの取得・複製・再配布・保存期間の利用条件。公開URLの長期アクセス可否と取得頻度。
- 予測タイルは通知時点で確保し、後続の実況タイルは公開遅延を見て回収する。予測対象のbasetime/validtimeを必ず保存する。
- 1通知の全予測フレームが必要かを通知種別で選定。取得不能時は欠測を明示。
- Storage容量とDB容量は別枠。**現行契約プラン・請求/容量上限の管理画面確認は未完了**。
- DB `bytea` も可能だがDB容量/バックアップ/読み書き負荷を増やす。大きいバイナリはStorage＋DBメタデータを第一候補とする。最終判断は実測後。
- 保存はまず通知が実際に出た登録地点のみ。通知が出なかったケースの見逃し率は評価できない。

## 次工程
公開JMAタイルの実ファイルを安全な頻度で少数取得して3方式のbytesを実測する。利用条件確認後、Storage/DBへの保存方式を選定。本番書込みやEdge Function改修は別途承認が必要。
