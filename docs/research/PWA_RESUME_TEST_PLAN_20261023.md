# PWA通知履歴・復帰診断：安全な実機検証手順（2026-10-23）

## 現在地
- 研究ブランチ: `research/pwa-feedback-resume-auth-20261023`
- 診断ユーティリティ: `lib/diagnostics/pwaResumeDiagnostics.ts`
- 履歴コンポーネントへの計測フック: `app/components/NotificationFeedbackHistory.tsx`
- **静的なコード照合のみ実施。ビルド・型検査・iPhone実機検証は未実施。**
- **main／本番／DB／匿名認証セッションへの変更なし。**

## 静的照合結果
- client componentの先頭ディレクティブは維持。
- mount/unmount、refresh開始/終了/例外、履歴sectionのDOM識別属性が研究ブランチに存在。
- 診断はwindowメモリ内の直近100イベントのみ保持。外部送信・token・匿名IDの記録なし。
- **注意**: フルページreloadやWebKitによるプロセス破棄でメモリ上の記録は失われる。これだけでreload有無を確証できない。
- **注意**: 診断コードは開発ブランチに置いただけで、実機PWAからはまだ利用できない。利用には検証用ビルドへの明示的な組み込み・アクセス方法の設計が必要。
- **注意**: 例外文字列には予期せぬ個人情報が含まれる可能性がある。共有前に内容を確認し、必要ならメッセージ全文の採取をやめて例外発生有無だけにする。
- **注意**: `refresh` はownerId依存で再生成されるため、初回取得でownerIdを設定した後、effectが再実行される。非同期競合の有無は未検証。

## 安全ゲート
1. 既存PWAを削除しない。Safari/Chrome/PWAのサイトデータやキャッシュを消さない。
2. `signOut`、匿名ログイン再作成、地点再登録、通知許可の再設定はしない。
3. 診断を本番に入れない。必要なら研究ブランチの独立プレビューで検証するが、プレビューで別の匿名IDを作らない。
4. 端末のセッションやtokenを外部へ送信しない。診断ログはイベント名・時刻・画面要素有無に限定する。
5. プレビューがiPhoneのホーム画面PWAと同等条件になる保証はない。再現しない場合は「本番の原因なし」と結論しない。

## 検証シナリオ（今後）
1. 現行PWAを通常起動し、履歴枠があることを記録。
2. iPhoneホーム画面へ戻り、初回復帰時の黒フラッシュと履歴枠の有無を観察。
3. もう一度同じ操作を繰り返し、二回目との差を記録。
4. PWA完全終了→再起動で履歴枠が戻るか記録。
5. Safariでは白フラッシュが毎回起きるか、履歴枠は残るかを記録。
6. Chromeは別認証領域として扱い、認証セッションなしメッセージが出る場合はそのままにする。
7. 計測可能になったら`pageshow.persisted`、`visibilityState`、history-mount/unmount、refresh開始終了、DOM存在の時系列を照合。

## 判定基準
- **refresh開始後にhistory-unmount**: React componentのアンマウントを疑う。ただし原因までは特定しない。
- **DOMが消えたがunmountなし**: document入れ替え／hydration／描画系の別経路を疑う。
- **pageshow persisted=true**: BFCache復元の手掛かり。falseだけではreload断定不可。
- **診断ログが突然初期化**: document再生成またはJS実行環境再起動の手掛かり。Safari/PWAの内部挙動を追加確認。
- **セッションなしメッセージだけ出る**: 認証セッションなし。履歴section自体の消失とは区別。
