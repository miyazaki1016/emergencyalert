# 点・面・併用のシャドー比較（2026-10-29）

[総覧](PROJECT_OVERVIEW.md) · [開発台帳](DEVELOPMENT_LEDGER.md) · [画像保存](RAIN_AREA_EVIDENCE_20261029.md)

## 目的・範囲
ユーザーの依頼「これ進めてもらえるかな？」に基づき、登録地点近傍の歯抜け・弱雨を対象に、点／面／併用を並行計算する。既存の通知判定・Push・点評価・画像回収は変更しない。専用ブランチ `feat/rain-area-shadow-20261029`。これは未校正の研究候補で、本番通知へ採用する処理ではない。[PR #101](https://github.com/miyazaki1016/emergencyalert/pull/101)で追跡。本番実行確認は末尾参照。

## 空間特徴
- 画像保存済みPNGと取得マスクを読み、PNGおよびRGBAのSHA-256を検証。マスクのSHA-256も解析結果に記録する。
- 登録地点の緯度経度から**画素内の正確な小数座標**を再計算。画素中心へ勝手に丸めない。緯度で地表距離へ換算し、250m／500m／1kmの円を各画素内8×8のサブサンプルで面積近似する。
- 雨域占有率＝雨色の既知面積／分類可能な面積。取得欠測、未知色は「雨なし」にせず、それぞれの比率とusableCoverageを保存する。取得済みの透明画素は現行パレットと同じく「レーダー表示上の雨なし」と分類するが、地上の無降雨の証明にはしない。
- <1、1〜5、5〜10、10〜20、20〜30、30〜50、50〜80、80以上の階級別面積比を保持。RGBAをmm/hの連続値に見立てた平均は作らない。
- 雨域の4近傍連結成分数、最大成分の面積比、最近接雨画素中心までの距離、中心の乾いた領域が完全に雨色で囲まれる場合の穴面積を記録。欠測・未知色に接する穴は確定しない。穴の画素を塗りつぶして元データを変更しない。
- 画像画素は独立したレーダー観測ではない。陸上の高解像度ナウキャストの公称格子は30分先まで250m、35〜60分は1km（気象庁 https://www.jma.go.jp/jma/kishou/know/kurashi/highres_nowcast.html 参照）。500mを主にする今回の面／併用候補は30分を超える予測を保留とし、解像度や地上雨量の真値をPNG画素数から創作しない。

## 比較候補 area-shadow-v1
- 主範囲500m、近傍確認250m、1kmは背景指標。250mと500mの分類可能面積95%以上が必要。この95%も暫定の品質ゲート。
- 面：500mの雨域占有率が20%／40%／60%以上でRAIN、各閾値の半分以下でNO_RAIN、中間は直前の状態を保つ。前状態が不明なら保留。
- 併用：中心RAINかつ500mが解除閾値以上、または500mが開始閾値以上かつ250mも解除閾値以上ならRAIN。中心NO_RAINかつ近傍も500mも解除閾値以下ならNO_RAIN。その他は前状態を保つ。離れた雨域だけでその地点も雨とはしない。
- 欠測や5分を超える時刻の穴で状態の持越しを切る。3コマが厳密に5分間隔で続き、その直前に反対状態が確認できる場合だけ、共通比較用の開始／終了時刻を記録する。
- 点候補にも同じ二値・3コマ比較ルールを適用するが、**これは現行通知エンジンの完全再現ではない**。現行通知のeventType／targetTime／interpretation／既存radar_resultはcurrentProductionに別途残す。
- 20/40/60%は検証用グリッドで、最適値・校正済み確率ではない。強雨への本番通知条件も変更しない。

## 未来情報の混入と比較の分母
- 元snapshotに実在する予測フレームだけを発表時刻baseTimeごとに分離して処理する。違う発表時刻を継ぎ合わせた3コマを作らない。元予測の重複フレームはエラーにする。
- 面／併用の予測候補には、当時の中心画素と一致した画像、取得時刻が予測有効時刻以前かつ解析実行時刻以前の画像だけを使う。同じURLでも、当時の周辺全体の同一性が証明できたわけではなく、研究用の回収画像であるという制約は続く。
- 取得不明・元画素不一致・有効時刻後取得・粗い予測格子・欠測などは理由を付けてINDETERMINATEにする。画像特徴そのものは遡及的な研究に利用できるよう残す。
- 3方式とも、判定時点より未来の予測だけをリードタイム付きで集計し、**同一時刻の既存の中心点レーダー実況**に対する一致を並行記録する。面方式だけ「範囲内のどこかで降った」を正解にして評価基準を緩めない。判定可能な3方式の共通サンプルで比較するSQLを用意し、各方式の保留件数と実況欠測件数も同時に出す。保留で難しいケースを除外しただけの一致率上昇を改善と呼ばない。
- これは中心実況との一致であり、地上の本当の雨との精度ではない。中心実況自体が歯抜けの場合、地上では正しい面判定が不一致になることも考えられる。この集計だけで面方式の採否を決めない。
- 利用者の天気回答は観測時刻・時刻情報の由来とともに別途SQLで参照する。回答が後から更新されても古いコピーを正解として固定しない。時間・場所・回答偏りの制約を考慮し、独立雨量計とも別扱い。
- 現在の対象は通知が出たケースのみ。見逃し率には無通知時刻の別サンプルが必要で、今回はまだ取得を追加していない。地点／雨イベントを分けて評価し、連続フレームの数を独立した事例数と呼ばない。

## 実行・保存・制限
- 独立Edge Function `shadow-rain`を5分ごとに実行。JMAへの追加アクセスはせず、保存済み画像だけを解析する。既存workerを呼ばず、Pushを送信しない。
- 受理済み通知のみ、1回2件・最大20画像/件・40秒予算。排他的claimと2分lease、更新時のlease_id照合。画像と点実況の回収が終わるまで再計算し、期限または試行上限で未完を明示。
- rain_area_shadow_resultsにアルゴリズム版・元画像ハッシュ・特徴・比較を保存。親評価の削除でcascade。保持期間は親と同じ最大90日。rain_shadow_runsは30日、PROBEを分離。
- 結果テーブル物理容量32MiB以上で新規claim停止（実行中バッチの限定超過はあり得る）。削除だけで物理容量が縮まらない場合があり、上限到達時は保守・保存方式を再検討する。
- RLS有効、anon/authenticatedの権限なし。service_roleだけが操作。アルゴリズム版を変更する場合は旧結果を残し、対象の再計算を別途設計する。
- PROBEは既存の固定気象地点の画像保存PROBEを再利用し、過去画像の時刻を表示する。架空の通知／精度サンプルを作らない。
- 切り戻しはshadow-rainのcron停止でよい。通知・点評価・画像回収を巻き戻す必要はない。
